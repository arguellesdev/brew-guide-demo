# Brew Guide: repo rules

Jaspr 0.23 app, server-rendered (`mode: server`, port 3015), with `jaspr_router` and a Gemini-backed API. Started as a Flutter Conf demo; now a personal playground for learning Jaspr and semantic HTML (the README still describes the talk).

## Role
Act as a senior full-stack engineer with a process-engineering mindset: typed inputs → rendering → predictable outputs, with every failure mode handled. When making technical decisions:
- Choose the simplest solution that meets the spec. No speculative abstractions or new dependencies without a stated reason.
- Name the trade-off when there are real alternatives (performance, complexity, maintenance), recommend one, and say why.
- Consider both sides of every change: what the server renders and sends, and what the browser receives and runs.
- Flag risks before acting: security (secrets, user input sent to Gemini), breaking routes or specs, and hard-to-reverse changes.
- Leave the code easier to change than you found it, but keep cleanups separate from feature work.

## Commands
- Run: `jaspr serve` from the project root → http://localhost:3015. Needs `GEMINI_API_KEY` in `.env`. `dotenv` reads `.env` from the working directory and also checks the shell environment. Never commit `.env` (gitignored). Don't add wrapper scripts that export the key; `.env` is the only place it lives.
- Build: `jaspr build`
- Check before finishing: `dart format lib` and `dart analyze` (page width 120, `jaspr_lints` enabled with `prefer_html_components`, `sort_children_last`, `styles_ordering`)
- No test suite yet. To verify a change, run the app and use the flows below.

## How a request flows
1. `/` renders `Home` → `MethodSelector`, all on the server. Each of the four method cards is its own `<form method=post action=/api/gemini>` with hidden `preference` and `method` inputs. The free-text box is a fifth form that sends only `preference`.
2. Inline `onsubmit` JS (`_onSubmitJs` in `method_selector.dart`) shows the full-screen `#loading` overlay and hides it again on bfcache `pageshow`.
3. `main.server.dart` adds a shelf middleware that sends `POST api/gemini` to `handleGeminiRequest` (`lib/handlers/gemini_handler.dart`).
4. The handler calls `recommendCoffee` (`lib/services/gemini_service.dart`, model `gemini-3.5-flash`, 30 s timeout, retries once on `busy`/`badResponse`).
   - Success → `302 /coffee?name=…&flavorNotes=a,b,c` (comma-joined).
   - Failure on a preset card → `302 /coffee?…&fallback=1` with the matching recipe from `lib/data/house_guides.dart`.
   - Failure on free text → `302 /?error=<GeminiFailure.name>&q=<text>` so the user can retry in one click.
5. `/coffee` (`lib/pages/coffee.dart`) is rebuilt entirely from query params in `lib/app.dart`. There is no server-side state or session.

The only `@client` component is `BrewFacts` (rotating facts inside the loading overlay). Everything else ships no Dart JS.

## Design system index (read before writing UI)
- **Tokens:** `lib/constants/theme.dart`
  - SCA palette: `scaCitrus`, `scaStrawberry`, `scaChocolate`, `scaFloral`, `scaBlueberry`, `scaFerment`, `scaWine`, `scaHerb`, `scaBay`
  - Surfaces/text: `colorBackground`, `colorSurface`, `colorBorder`, `colorTextDark`, `colorTextMid`, `colorTextMuted`
  - 10% tints: `scaWineTint`, `scaHerbTint`
  - Fonts: Playfair Display (headings), DM Sans (body), loaded through a Google Fonts `css.import`
  - Global element styles (`html, body`, `h1`–`h3`, `p`) also live here
- **Specs:** `lib/specs/` contains `method_selector.md`, `coffee_detail.md`, `gemini_service.md`, `compare_methods.md` (see "Known drift")
- **Errors:** `GeminiFailure` in `lib/services/gemini_service.dart` (`busy`, `timeout`, `badResponse`, `unavailable`, `notABrewMethod`), shown to users through `_errorMessages` in `lib/components/method_selector.dart` and `lib/pages/compare.dart`, which also have the UI-only `empty` key. Shared UI: `ErrorBanner`, `LoadingOverlay` + `loadingOnSubmitJs` in `lib/components/`
- **Routes:** `/` (home, params `error`, `q`), `/coffee` and `/compare` in `lib/app.dart`; `POST /api/gemini` and `POST /api/compare` in `lib/handlers/gemini_handler.dart`
- **Static assets:** `web/` (`images/logo.svg`, `docs/*.pdf` linked from the home page's "Run Guide")

## Jaspr gotchas
- `lib/main.server.options.dart` and `lib/main.client.options.dart` are generated by `jaspr_builder`. Don't edit them. They regenerate when you add or remove `@css` getters or `@client` components (with `jaspr serve` running, or via `dart run build_runner build`).
- `@css` styles are global. Scope every rule under a component-prefixed class (`.method-selector …`, `.coffee-detail …`).
- `initState` also runs during SSR. Guard browser-only work with `kIsWeb` (see `brew_facts.dart`).
- Jaspr is pre-1.0, so APIs shift between minors. Check the 0.23 API before reaching for patterns from older docs.

## Rules
1. No raw `Color('#…')`, font names or one-off colors outside `theme.dart`. Add a missing token there first.
2. Follow the matching spec in `lib/specs/`. If behavior or structure changes, update the spec in the same change. New components and services get a spec.
3. Every UI handles idle, loading (skeleton or informative overlay, no bare spinner), empty (tells the user what to do) and error (human message + retry).
4. New failure cases: add a `GeminiFailure` value and a matching `_errorMessages` entry. Never show raw exceptions to users.
5. Server-render by default. Use `@client` only for real interactivity, kept as small as possible (like `brew_facts.dart`).
6. `const` constructors and data wherever possible. Typed parameters and callbacks, never `dynamic`. Prefer slots (`Component` parameters) over big monolithic components.
7. Semantic HTML first, ARIA only where meaning isn't obvious. Hit targets at least 48×48 px, keyboard-usable, visible focus.
8. Text uses `rem`/`em`. Long text is clamped or ellipsized. Layout works on mobile, tablet and desktop.

## Output for new components or features
1. System & flow architecture (tree, state pipeline, SSR vs `@client`)
2. Interface spec (typed parameters, events)
3. Implementation
4. Lifecycle scenarios (standard, loading, empty, error, edge cases)
5. QA (how it was verified, failure modes to watch)

Small fixes and questions skip this format.

## Known drift (code is the source of truth until fixed)
- `specs/method_selector.md` describes cards as `<a href="/coffee/:method">`. In the code they are POST forms to `/api/gemini`, and there is no `/coffee/:method` route.
- `specs/coffee_detail.md` points to `lib/components/coffee_detail.dart`. The real file is `lib/pages/coffee.dart` (class `Coffee`).
- `specs/gemini_service.md` says the key comes from `Platform.environment`. The handler actually reads it through `dotenv` and passes it into `recommendCoffee`.

## Known cleanup
- `primaryColor` in `theme.dart` is a leftover from the template counter. Remove it once nothing uses it.
- Some styles break Rule 1 with raw colors. `coffee.dart` still uses the alpha tint `#3263591a` (now the `scaHerbTint` token), and `method_selector.dart` has a hover shadow `#2b6a5d1a`. Move these into tokens when you next touch those files.
